# 项目约束与评估框架

> 记录时间：2026-10-17
> 用途：五个资料文件夹横向对比时的统一标尺，避免「把不同战场的方法论直接混用」。

## 一、项目目标

做一个自己的「新词雷达」：**发现热点词 / 新词**。

> **范围边界（2026-10-17 确认）**：本项目只做「发现新词」。发现之后怎么上站、怎么生产页面，不在本项目范围内。下文提到的「1 天上站」只作为判断一个词**值不值得做**的时间窗口参照，不是设计目标。

## 二、五条硬约束（主人确认）

| # | 约束 | 对设计的直接影响 |
|---|---|---|
| 1 | 上站周期：**1 天**（仅作窗口参照） | 优先天级窗口的命名型新词；慢线只做储备；雷达输出到「词 + 证据 + 决策」为止，不负责页面生产 |
| 2 | 站型不限：工具站 / 内容页 / 落地页 / 游戏页都可 | 判据从「能不能做工具」改为「能不能带来流量」；变现是加分项，不是门槛 |
| 3 | 优先免费 API；但 DataForSEO / AISA / GoAnyAPI 已注册并有 key，必要时该用就用 | 免费栈做日常扫描，付费栈做关键验证；单次运行成本控制在 $2–3 量级 |
| 4 | 多语言多市场；**英语 / 美国优先级最高** | 信号源要能加 locale；首批 en-US，其他语种发现合适机会也不忽略 |
| 5 | **出海优先，国内不作为目标市场** | 信号源以海外为主；TrendRadar 只借工程件，不借中文热榜数据；备案/国内生态不作为约束 |

## 三、统一评估框架

每个文件夹固定输出四栏：

1. **信号源**：从哪里发现「有新需求」的迹象
2. **发现机制**：怎么从信号变成候选词
3. **判断链**：候选词怎么被验证 / 淘汰
4. **工程形态**：手工 SOP、半自动脚本、还是全自动 pipeline

再加两个判断：

- **它挖的是哪种词**：组合型新词 / 命名型新词 / 老词 / 新站
- **它默认的战场**：搜索 / 社区 / 供应侧；窗口长度

## 四、「1 天上站」倒推的硬指标

- 发现 → 决策 ≤ **2 小时**
- 决策 → 页面可访问 ≤ **1 天**
- 因此必须具备：模板库 + 自动生成 title/meta/JSON-LD + 一键部署
- 窗口 < 1 天的词不值得做（除非模板已就绪、改个数据就能上）

## 五、五种「词」的定义（后面持续使用）

| 类型 | 定义 | 例子 |
|---|---|---|
| 命名型新词 | 全新专名，之前不存在 | Strata、Seedance、Nano Banana |
| 组合型新词 | 旧词根 + 新修饰，新出现的搜索表达 | ai tattoo generator、kling ai motion poster |
| 上升期老词 | 已存在但正在起量 | ai humanizer、invoice generator |
| 成熟老词 | 长期有量、竞争充分 | pdf converter、free vpn |
| 新站/新产品 | 供应侧的实体，本身未必是关键词 | 某个刚上线的 vercel.app 子站 |

## 六、最后需要一起回答的问题

- 快线（命名型）与慢线（组合型）的资源配比
- 首批市场与语言
- 付费 API 的月度预算上限
- 页面模板覆盖哪些站型（工具 / 内容 / 游戏 / 导航）
