## 0. 一页结论

我们要做的不是「关键词工具」，而是一台**面向出海 AI 市场的新词雷达**：

```
两条产线  +  一条统一判断链  +  一份可复盘的记忆
```

- **快线（天级）**：命名型新词。X / Hugging Face / GitHub / Product Hunt / Hacker News / sitemap / 新站。
- **慢线（周/月级）**：组合型新词。词根 × 品类 + Google Autocomplete + Trends + 大站子页面/免费托管子域名。
- **统一判断链**：抽词 → 归一 → 新词判定 → 证据 → 通用词 → 需求 → 竞争 → 决策 → 复盘。
- **记忆**：`first_seen`、每信号首次出现时间、每次决策、每次复盘；用这些数据反过来给信号加权。

首版只交付快线 + 关键词表；慢线放在第二阶段。**不做页面生成、支付、部署、推送。**

### 3.1 快线（首版 P0/P1）

| 信号 | 来源 | 抓什么 | 成本 | 状态 | 优先级 |
|---|---|---|---|---|---|
| X | 官方 labs + 选中 blogger | 首次使用的新名字 | $0.003/账号 | 已有 | P0 |
| Hugging Face | trending models/spaces | 新进榜模型 / Space | 免费 | 已有 | P0 |
| GitHub | 新建仓库爆发 | 单仓库 + owner 变体 | 免费 | 已有 | P0 |
| Product Hunt | 日榜 / 新上架 | 新产品名、tagline | 免费（API v2，需 token） | 已有（M3） | P0 |
| Hacker News | Algolia Search | Show HN / launch / 新名字 | 免费 | 已有（M3） | P0 |
| Sitemap | AI 导航/MCP 站 | 新 URL 共享词 | 免费 | 已有 | P1 |
| 官方发布页 / changelog | OpenAI、Google、DeepMind、HF、Mistral、MS Research | 新模型/新功能名 | 免费（RSS） | 已有 6 个 feed（M3） | P1 |
| 新站 | 90 天内注册且已有自然流量 | 新域名、词的来源 | ~$0.13/查询 | 已验证（2026-10-17） | P1 |
| Reddit 求助 | 12 种问法 | 用户视角的 job | ~$0.12/周 | 已有 | P2 |
| TrustMRR | 付费产品增长/新上榜 | 已被验证的付费需求 | 免费（需 key） | 已有 | P2 |
| GSC | 自己的站 | 首次曝光 query | 免费 | 已有，默认关 | P3 |
| 免费托管子域名 | vercel.app / lovable.app 等 | 低权重新站 | 付费查询 | 待加 | P2 |
| 大站子页面 | Similarweb new pages | 大站新增的高流量页面 | 付费 | 待加 | P3 |

**Sitemap / 新站：是回声，不单独进复盘。** 这两个信号产出的是「别人页面上出现的词」，不是「有人在说一个新东西」：`bitbucket`、`zotero` 这种二十年的产品会因为竞品新开一页而反复出现。所以只由这两个信号发现的名字，落库时标 `status='echo'`：`due()` 不为它排期，`summary()` 的 `pending` 也不计。一旦 X / HF / GitHub 也报了同一个词，状态升回 `new`，照常进 14 天复盘；状态只会从 echo 升到 new，不会因为第二天只撞到一条 sitemap 就降回去。

代价是这两个信号不再有 `hit rate` 和 `median_lead`。它们的准确率改由**名字精度抽检**代理：每次运行从 `sitemap` / `newsite` 产出的候选里抽 10 个，标「真新名字 / 已存在产品」，按月汇总。M5 的验收项因此拆成两条：X / HF / GitHub 用 `hit rate`，Sitemap / 新站用名字精度。

**M3 落地（2026-10-17）**：HN 取 Show HN、过分数门槛，每个 objectID 只报一次；官方 feed 只读最近 7 天（OpenAI 的 feed 带 1,299 条历史，不设窗口第一次运行就会把整个存档当新闻）。官方标题必须是一个名字：开头最多三个词，先去掉 Introducing/Welcome 和动名词，且名字要带数字或版本、或以发布词开头；客户故事（"How Itaú is building…"）和清单式标题丢掉。Anthropic 与 Meta AI 没有可用 feed（2026-10-17 实测 Anthropic 的 7 条路径全 404），所以官方源是 6 家。一个 feed 返回的是网页而不是 feed 时，与网络失败同等对待：记一行，不拖垮别的 feed。

PH 走 GraphQL，`PH_API_KEY` 是 dashboard 的 developer token；取 AI 话题下最近 26 小时按票数排的前 50 条，票数 ≥50 才要，名字取冒号前的品牌词加上冒号后的第一个词（`Notion: Context for your agents` → `notion context`），整体等于已知厂商且没有版本号的名字丢掉。

新站的 filter 没有坏：2026-10-17 用 `scripts/new_sites_probe.py --query ai` 探了一次，status 20000、9 条、$0.131。M0 记的「filter 被拒」是从上游继承的说法，本项目没有复现过。真正的毛病是 `aisa.call()` 会把失败的调用从结果里丢掉，报告于是写成「没有新站」；现在每个源都有一行数据状态，失败的查询、失败的 feed、跳过的源都会点名。

M3 的验收「每个新源 14 天后有 hit rate」只保证结构：新词进 `terms` 后照常进复盘池，`summary()` 的 by-signal 表按 `source` 分组，不需要额外接线。数字要等这些词满 14 天，归 M5 验收。

## 4. 判断链

### 4.1 抽词（Extract）

- 英文：保留现有规则（大写、数字、内部大写、版本号），但增加：
  - 小写名字：用已知 AI 词表 + LLM 兜底，不单靠大小写。
  - 尾词清理：去掉 `is / now / launch / released / available / today` 等尾词（修复 `kling 4.0 is`）。
- 非英文：语言特定分词（CJK 用 jieba 等），不依赖大写。
- 来源：帖子正文、README、产品描述、页面 title/H1/meta、sitemap slug、产品名。

### 4.2 归一与别名（Normalize / Entity Resolution）

必须先做，否则同一个发布会产生多条 lead：

```
muse spark open / spark open / meta muse spark open  →  canonical: muse spark open
meta omnilingual asr / omnilingual asr               →  canonical: omnilingual asr
```

规则（从保守开始，宁可重复，不要误并）：

1. **先归一**：统一大小写、连字符/下划线/空格；去掉 URL、@handle、首尾标点。
2. **只在同时满足时合并**：
   - 一个词是另一个的**连续词元子序列**；
   - 同源 / 同帖 / 同日（至少满足一个，最好两个）；
   - 多出来的词是 **maker**（`meta`、`openai`、`google`、`anthropic`）或格式/版本标点，**不是** `pro` / `sol` / `max` 这种变体后缀。
3. **不合并**：只共享一个通用词（`open`、`beam`、`glass`）；`gpt 6.1` 与 `gpt 6.1 sol`；`gpt-6 astra` 与 `gpt-6 astra pro`。
4. **canonical 选择**：优先官方模型 ID / 帖子里的完整写法；其次是最短的可搜索形式；`aliases` 保留其余写法。
5. `known_terms` 用词边界匹配，不用子串（避免 `ai` 隐藏一切）。

典型合并：

```
deepseek v4.1 flash 1017  ↔  deepseek-v4.1-flash-1017   → canonical: deepseek v4.1 flash 1017
hy memory                 ↔  hy-memory-30b-a3b          → canonical: hy memory
mirelo sfx 2.0            ↔  mirelo sfx                 → canonical: mirelo sfx 2.0
muse spark open           ↔  meta muse spark open        → canonical: muse spark open
```

**校准集**：50 对正例（同一实体）+ 50 对负例（共享词但不同实体）。验收报 **entity precision ≥95%**（误并比重复更贵）、recall ≥80%。

### 4.2b 选择偏差（M0 暴露）

现在的 `report.leads` 排序是 `X > HF > breakout > sitemap`，前 20 个候选名额被 X 占满；关键词表每天只读 5 个名字，也是从这 20 个里取。结果：`deepseek v4.1 flash 1017`（HF 0.95）、`hy memory`（HF 0.90）、`beam 1.0`（HF 0.90）、`figcraft`（GitHub 0.90）都没进关键词表。

修法：

- 实体归一之后再选词；
- 按**信号配额**或综合分选（例：X 2 个、HF 1 个、breakout 1 个、sitemap 1 个）；
- 加 fixture 测试：同一份报告里 X/HF/breakout 都有高分词时，选出的 5 个不能全是 X，单一信号不超过 60%。

### 4.3 新词判定（Novelty）

- **`first_seen` 定义「新」**，不是 Trends baseline。
- 60 天词表内出现过 → 不是新词。
- 与 `known_terms` 重合 → 标记「已覆盖」，仍可展示，但不进关键词表。
- 不要求「从未存在」；只要求「雷达第一次看到」。

### 4.4 名字判断（Judge）

保留 LLM judge，但做三件事：

1. **校准集**：200 个词，人工标注「专有名字 / 普通词 / 片段」，测 precision/recall。
2. **双阈值**：报告阈值 0.6；进关键词表阈值 0.8。
3. **输出 canonical 建议**：让模型顺便给一个规范化的名字（可选）。

### 4.5 证据与通用词（Evidence → Generic Terms）

保留 `usecases.py` 的主流程，补三处：

1. **证据源**：X 高赞帖子、README、产品描述、页面 title/H1/meta、Reddit 帖子、YouTube 评论。
2. **用户视角**：除了「这个产品能干什么」，再问「一个没听过这个产品的人，会怎么搜这个 job」；这是 jason 文章的核心。
3. **相关搜索**：GoAnyAPI 的真实共搜词，分成长尾 / 通用 / 共搜；比模型提议强。

### 4.6 需求（Demand）

**新词不能用 Google Ads 月搜当门槛**——新词通常没量，且数据滞后约两个月。

用两层指标：

**A. 领先指标（新词主用）**

| 指标 | 含义 |
|---|---|
| X 账号数 / 点赞 / 点赞速度 | 传播强度 |
| HF rank / likes / copies | 模型热度 |
| GitHub stars/day / delta | 仓库爆发 |
| PH upvotes / comments | 产品关注 |
| HN points / comments | 技术社区关注 |
| Reddit score / comments / asks | 用户是否在主动求工具 |
| Trends shape（rising/holding/fading） | 是否真的在起势 |
| Related queries 是否出现 | 真实搜索行为的强证据 |

**B. 搜索量（老词/通用词主用）**

- Google Ads 月搜：只对已存在、能被计量的通用词使用。
- 没有量时，标记 `volume_status = unknown`，**不要丢掉这个词**。
- 有量时，用 `volume_status = known`；低于阈值标 `below_threshold`，但仍保留。

**C. 基准词篮子（替代单一 `gpts`）**

单一基准词自身涨跌会让所有尺寸失真。改成 5–6 个跨品类的稳定基准：

| 候选 | 品类 | 备注 |
|---|---|---|
| `chatgpt` | 品牌锚 | 量大、稳定 |
| `ai image generator` | 图片 | 通用词 |
| `ai video generator` | 视频 | 通用词 |
| `text to speech` | 语音 | 通用词 |
| `pdf converter` | 工具/转化 | 非 AI，稳定 |
| `canva` | 品牌锚 | 稳定 |

**入篮标准**：90 天窗口里，最后 30 天均值对前 30 天均值的斜率在 ±20% 内（判的是最近一个月的走向，不是整段 90 天的回归）；Google Ads 月搜月环比 ±30% 内；无单日 3 倍以上尖峰；至少覆盖 3 个品类。

**合成算法：**

1. 目标词分别与每个基准做 pair 查询，得到 `target/benchmark` 比例；
2. 乘以该基准的日搜（月搜 / 30）；
3. 取中位数作为 `per_day`；
4. 基准日搜每月重算；某个基准斜率超过 ±20% 就替换。

**失败降级**：少于 2 个基准可校准时，`per_day=null`、`size_status=uncalibrated`，只报 Trends 形状；表继续出，不再整表停摆。

**成本**：5 个基准 × 5 个名字 × $0.0012 ≈ **$0.03/天**。

### 4.7 竞争（Winnability）

留住 new-term-radar 的 SERP 判断，但修三个问题：

1. **DR 缺失不要直接判 crowded**：`weak=None` 时用 KD/广告/页面类型兜底；仍无法判断则标 `unknown`。
2. **新词首页还在形成**：第一次读（day 0）+ 第二次读（day 3/7）；第二次才作准。
3. **加供应密度**：`intitle` 新增页数、sitemap 新增页、广告主数量；不只看 DR。

输出：

- `open`：弱站 ≥3 或 KD <20。
- `mixed`：中间。
- `crowded`：无弱站且 KD ≥40，或明确的强站锁定。
- `unknown`：数据不足（新词的常态）。

### 4.8 决策（Decision）

| 决策 | 条件 |
|---|---|
| **prioritize** | 正在涨/保持高位 + 需求分达标 + 竞争 open/mixed |
| **watch** | 涨但规模小/太早；或 flat 但稳定有量；或 crowded 但在涨（降级） |
| **skip** | 已回落；或 flat 且小；或 crowded 且不涨 |

**规模未知时**（基准篮子可校准项 <2，或这个名字没有 pair 数据）：`per_day=null`，决策改看领先规则——≥2 个独立信号发现它且名字分 ≥0.8 算「大」，按走势落到 prioritize / watch / skip；表里 `规模` 列会标 `uncalibrated` 或 `unknown`。已知的规模永远优先于领先规则。

每行附带：

- `confidence`：high（≥2 个独立信号 + 有量/相关搜索 + 有竞争数据）/ medium / low。
- `window`：fast（命名型，<14 天）/ slow（组合型，>14 天）。
- `next_check`：1d / 3d / 7d / 14d。
- `why`：一句人话，引用证据。

### 4.9 复盘（Review）

**谁进复盘池**：`terms` 里 `status` 不是 `echo` 的词。只由 sitemap / 新站发现的词是回声，不进池（见 §3.1）。

从关键词表回流的通用词（`usecase_leads`）只有拿到搜索量（`volume_status` 为 `known` 或 `below_threshold`）才进池：零月搜的短语没有需求证据，进池只会花掉 10-31 之后的复盘预算。它们仍然留在当天的表里，只是不进 14 天复盘。


**把「名字是真的」和「搜索起来了」分开评。**

| 指标 | 含义 |
|---|---|
| `name_real` | 这个名字是否真实存在（人工抽检/多源确认） |
| `search_rise` | Trends 是否在报告后上涨 |
| `persistence` | 是否在多个信号/多天持续出现 |
| `lead_days` | 雷达比 Trends 早几天 |
| `signal_hit` | 哪个信号最先发现它 |

复盘窗口：

- 快线：24h / 72h / 7d / 14d。
- 慢线：14d / 30d。

输出：每个信号的 `hit_rate`、`median_lead`、`false_positive`。**用这些数据决定下一版加/减哪个信号。**

## 5. 数据模型

建议新建一套干净的表；**不弃用旧 `leads`**，用一次性脚本迁移。

```sql
-- 词条
CREATE TABLE terms (
  id            INTEGER PRIMARY KEY,
  canonical     TEXT NOT NULL UNIQUE,
  aliases       TEXT NOT NULL DEFAULT '[]',   -- JSON
  first_seen    TEXT NOT NULL,
  last_seen     TEXT NOT NULL,
  name_score    REAL,
  window        TEXT,                          -- fast / slow
  confidence    TEXT,                          -- high / medium / low
  decision      TEXT,                          -- prioritize / watch / skip
  known         TEXT,                          -- 已覆盖的 known_term
  status        TEXT DEFAULT 'new',            -- new / watching / archived
  created_at    TEXT,
  updated_at    TEXT
);

-- 每个信号对同一个词的首次出现
CREATE TABLE term_signals (
  id            INTEGER PRIMARY KEY,
  term_id       INTEGER NOT NULL REFERENCES terms(id),
  source        TEXT NOT NULL,                 -- x / hf / github / ph / hn / sitemap / newsite ...
  source_id     TEXT,                          -- 账号、repo、URL、产品
  first_seen    TEXT NOT NULL,
  evidence      TEXT,                          -- 原话/标题/描述
  url           TEXT,
  score         REAL,
  metadata      TEXT DEFAULT '{}'              -- JSON：likes、stars、rank...
);

-- 关键词表（名字 + 通用词）
CREATE TABLE keywords (
  id            INTEGER PRIMARY KEY,
  term_id       INTEGER NOT NULL REFERENCES terms(id),
  phrase        TEXT NOT NULL,
  kind          TEXT NOT NULL,                 -- name / generic
  brand         INTEGER DEFAULT 0,
  is_name       INTEGER DEFAULT 0,
  established   INTEGER DEFAULT 0,
  volume        INTEGER,
  volume_month  TEXT,
  volume_status TEXT,                          -- known / unknown / below_threshold
  per_day       INTEGER,
  trend         TEXT DEFAULT '{}',             -- JSON：shape/size
  competition   TEXT DEFAULT '{}',             -- JSON：verdict/weak/kd/ads...
  decision      TEXT,
  confidence    TEXT,
  created_at    TEXT,
  updated_at    TEXT
);

-- 复盘（一个词/关键词可以有多个窗口）
CREATE TABLE reviews (
  id            INTEGER PRIMARY KEY,
  term_id       INTEGER NOT NULL REFERENCES terms(id),
  keyword_id    INTEGER REFERENCES keywords(id),
  days          INTEGER NOT NULL,              -- 1 / 3 / 7 / 14 / 30
  checked_at    TEXT NOT NULL,
  name_real     INTEGER,
  search_rise   INTEGER,
  persistence   INTEGER,
  lead_days     INTEGER,
  metrics       TEXT DEFAULT '{}'
);

-- 每次运行
CREATE TABLE runs (
  id            INTEGER PRIMARY KEY,
  command       TEXT NOT NULL,
  started_at    TEXT,
  finished_at   TEXT,
  cost_micros   INTEGER DEFAULT 0,
  stats         TEXT DEFAULT '{}',
  errors        TEXT DEFAULT '[]'
);
```

设计原则：

- `terms` 存「词」，`term_signals` 存「证据」，`keywords` 存「可做的搜索词」，`reviews` 存「结果」。
- 所有 JSON 字段只放可变结构；可筛选的维度单独建列。
- 时间统一 ISO 日期；成本统一 micro-USD。

### 5.1 从旧 `leads` 迁移

`state/radar.db` 里已有 75 条 lead（10-16 基线 52 条已备份在 `state/backup-2026-10-16/`）。不要静默丢：

- `leads` → `terms`：`term`、`first_seen`、`last_seen`、`named`、`variants`、`known`；
- `signals` JSON → `term_signals`：每个 kind 一行，`first_seen` 用 lead 的首次时间，`evidence` 用 notes；
- `reviewed_at / verdict / lead_days / trends` → `reviews`：`days=14`；
- 10-16 与 M0 的运行记录 → `runs`，作为校准参照；
- 迁移脚本 `scripts/migrate_leads.py`；迁移后对账条数、first_seen、review 状态；旧 DB 保留。

## 6. 运行节奏

首版**不做定时任务、不做推送**，只保留手动命令：

| 命令 | 频率 | 作用 |
|---|---|---|
| `python -m radar sources` | 每天 1–3 次 | 只跑快线源头（X/HF），有新名字才出报告 |
| `python -m radar daily` | 每天 1 次 | 快线全量 + 关键词表 + 复盘 |
| `python -m radar keywords "name"` | 按需 | 对指定名字生成关键词表 |
| `python -m radar leads` | 按需 | 看已有 lead 和复盘结果 |

成本控制：

- M0 实测 $0.341/次；目标 $0.3–0.5/天，日上限 $1；加 PH/HN 后仍接近免费。
- 每次运行记录 `cost_micros`；超过预算时只跑免费信号。
- 缓存键是 `(term, phase)`：day0 与 day3 是两个 phase；同一个 phase 7 天内不重复跑。

## 9. 成功指标

| 指标 | 目标 |
|---|---|
| 名字精度 | ≥80%（人工抽检 50 个） |
| 实体精度 | ≥95%（50 对正负例；误并比重复更贵） |
| 名字召回 | ≥70%（用已知新 AI 名字做 7 天回测） |
| 领先时间 | 中位数 ≥3 天（相对 Google Trends） |
| 度量完整性 | 30 词 golden set 通过；无「没量就丢」；基准失败时 `per_day=null` 且表仍出 |
| 产出量 | 参考项，不作门禁；全 skip 不算失败，假阳性才算 |
| 成本 | ≤$1/天（M0 实测 $0.341） |
| 可靠性 | 任何源失败都在报告里写明；薄表必须解释 |
| 复盘 | 14 天后每个信号有 hit rate；至少一个信号 >50% |

## 10. 风险与边界

| 风险 | 处理 |
|---|---|
| LLM 判错名字 | 校准集 + 双阈值 + 人工抽检 |
| 实体误并 | 保守合并规则 + 50 对正负例 + entity precision ≥95% |
| 选词偏差 | 实体归一后按信号配额选词；单一信号 ≤60% |
| 搜索量滞后 | 新词用领先指标；量只做参考；不硬门槛 |
| 基准词漂移 | 一篮子基准 + 月度重校准；无法校准时 `per_day=null` |
| 数据源失败/涨价 | 每个源独立降级；记录成本；免费源兜底 |
| 多语言复杂 | 首版 en-US；数据模型预留 locale；不假装支持 |
| 品牌/商标词 | `brand=true` 标记；不自动做站；由人判断 |
| 许可证 | new-term-radar 是 MIT，可 fork；TrendRadar 是 GPL-3.0，**不抄代码** |
| ToS | X 走 AISA；Reddit/TrustMRR 不转售；PH/HN 遵守 API 条款 |
| 过拟合 AI | 垂直包隔离；游戏/娱乐另做源与词根，不混 stop words |
