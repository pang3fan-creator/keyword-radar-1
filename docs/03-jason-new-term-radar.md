# jason / new-term-radar：唯一跑通「名字 → 通用词 → 决策 → 复盘」的闭环

> 来源：`gitignore/jason/` 实战复盘 + `new-term-radar/`（v0.4.0）
> 结论：它是五个文件夹里最接近「新词雷达」目标的项目，应该作为主骨架。但它强在**发现**，弱在**度量**；强在**英文 AI 圈**，弱在**多语言/多市场**。

## 一、两篇内容要分开看

| 内容 | 性质 | 价值 |
|---|---|---|
| 《5 天 1500 刀实战复盘》 | 单站案例，不是方法论 | 验证「新词窗口」真实存在；暴露两个雷达没覆盖的信号 |

### 发现机制

- **名字抽取**（`terms.names`）：大写词、带数字（Qwen3.8）、内部大写（HyperFrames）；名字后的数字并入（Opus 5.5）；相邻名字词最多拼 3 个；标点/中文会截断。
- **novelty**：名字不在过去 60 天的账号词表里；两个账号提到即入选，一个账号需要「强名字 + 100 赞」。
- **合并**：多个信号命中同一个词 = 最强 lead；LLM judge 给 0–1 的「这是不是专有名词」分数。
- **排序**：先看是否达到名字阈值，再看信号数、信号出现早晚、格式（视频 > 语音 > 图片 > 文字）、名字分数。

### 判断链（核心）

**A. 名字判断**：`gpt-4.1-mini`，每 25 个词一次，0–1 分，报告阈值 0.5，进关键词表阈值 0.8。

**B. 关键词表（`usecases.py`）八步：**

1. **证据**：X 高赞帖子（每名 12 条）+ GitHub README（3000 字）+ 产品描述。
2. **提议**：`claude-sonnet-4-6` 读证据，写 2–5 个词的「普通人会搜的词」，必须带一句证据引用，最多 6 个。
3. **相关搜索**（可选 GoAnyAPI）：名字的长尾、通用候选、共同搜索的其他新名字。
4. **筛选**：第二次 LLM 调用，打分相关性、品牌、是否别的名字、是否老产品；相关性 <0.6 丢掉。
5. **量**：Google Ads 批量查询，月搜 <50 丢掉。
6. **Trends**：每个词查两次——单独看形状，和基准词 `gpts` 一起看大小；丢掉最后 2 天未结算数据。
7. **尺寸**：通用词用自己的月搜 × 近期/当月 Trends 比例；名字没有量，用基准词反推；基准词由月搜 ≥1000 的通用词校准。
8. **首页竞争**：SERP 前 10、DR、KD、广告、intitle、广告主；`open / mixed / crowded`；crowded 的 prioritize 降为 watch。

**C. 决策**：`prioritize`（涨、还在高位、日搜 ≥300）/ `watch`（涨但小、太早、或稳定有量）/ `skip`（回落或没量）。

**D. 复盘**：14 天后查 Trends，变体峰值 ≥ 基线 2 倍且 +10 分算 hit；记录 lead_days；按信号统计命中率。

### 工程形态

- 纯标准库 Python 3.10+；SQLite `radar.db`；gzip 快照；CLI（daily/sources/keywords/leads/pains/mcp）。
- 3 个 Agent Skills；MCP 三个工具（recent_leads / keyword_table / run_radar）。
- GitHub Actions：sources 每 8 小时，daily 每天一次；state 走 cache。
- 成本：示例配置约 $0.30/天；X $0.003/账号；Trends $0.0012；量批量 $0.09；关键词约 $0.05/名 + $0.09/次。
- 降级诚实：任何信号失败都会在报告里写出来；「薄表不等于安静的市场」。

## 三、真实运行数据（2026-10-16）

- 35/35 个 X 账号，660 条帖子；187 个爆发仓库；12 个 sitemap，其中 glama 新增 11,200 个 URL，toolify 读取失败。
- 读了 5 个名字：muse spark open、kling 4.0 is、gpt-live-1.1、meta omnilingual asr、omnilingual asr。
- 提出 29 个通用写法，13 个通过相关性筛选，**只有 2 个月搜 ≥50**。
- 关键词表 7 行，**全部 skip**；`gpts` 当天无法校准，名字没有日搜估算。
- 状态库 52 条 lead：breakout 17、usecase 12、x 10、cosearch 7、sitemap 3、hf 2、hf+x 1；**全部 pending，14 天复盘还没开始**。
- `muse_baseline.md` 是另一次手工实验：18 个写法 → 6 个相关 → 1 个有量（ai coding agent，206/天，skip）。

**结论：发现层能出货，度量层经常出不了货。** 报告自己写「今天没法校准基准词 gpts」，这是系统最真实的瓶颈。

## 四、它挖的是哪种词

| 层 | 产出 | 说明 |
|---|---|---|
| 发现 | 命名型新词 | X/HF/GitHub/sitemap/收入/求助 |
| 解释 | 通用词（名字背后的 job） | 名字短命，通用词长命 |
| 判断 | prioritize / watch / skip | 需求 + 竞争 |
| 复盘 | hit / miss / no_data | 验证信号 |

**它不是**：老词挖掘器、供应侧新站挖掘器（new_sites 坏了）、多语言雷达。

## 四半、它不管上站（范围确认）

`new-term-radar` 只做发现与判断，**不生成页面、不接支付、不部署**：

- 依赖为零；可选依赖只有 `markdown`（邮件）和 `mcp`（MCP 服务）。
- 输出是 Markdown/JSON 报告 + SQLite 记录 + 邮件/MCP，没有模板、CMS、部署脚本。
- `revenue.py` 里的 Stripe 只是 TrustMRR 的数据口径说明，不是支付集成。
- `new_sites.py` 是「发现新站」信号，不是「建站」功能。
- jason 的 1500 刀站是另一件事：他用 TanStarter 模板 + Stripe 自己上的，雷达只负责找词。

这也是我们把项目范围收窄到「只做发现」的原因：上站是另一个「站点工厂」层，需要模板、内容生成、支付、部署，和雷达不是同一个工程。

## 五、值得偷的 10 个设计

1. **名字优先，通用词第二**：解决「名字属于别人、job 属于所有人」的问题。
2. **读两次**：出现当天 + 3 天后，因为发布日只有公告、没有用法。
3. **14 天闭环复盘**：按信号统计命中率，这是大多数雷达没有的。
4. **基准词定尺寸**：名字没有搜索量，用 `gpts` 反推；通用词校准基准。
5. **首页竞争判断**：弱站数量 + KD + 广告 + intitle + 广告主；crowded 降级。
6. **证据约束 LLM**：必须引用原话；只有公告没有具体 job 就返回空。
7. **相关搜索**：GoAnyAPI 的真实共搜词，比模型提议强；长尾/通用/共搜三分类很实用。
8. **降级报告**：哪个源失败、表为什么薄，全部写出来。
9. **SQLite + 快照 + first_seen**：有记忆才能复盘；变体（niko/niko1221）考虑得好。
10. **成本透明 + 批量上限 + Skills/MCP**：不只是脚本，是 Agent 可用的工具。

## 六、不能照抄 / 必须改的 12 个坑

1. **多语言是硬编码的**：量/SERP/竞争全部 `language_code="en"`、`location_code=2840`；`lang` 只翻译报告；`names()` 分词器是 ASCII-only，中文只当分隔符（测试里明确写了 `test_names_breaks_on_chinese_text_between_words`）。纯中文名字抓不到。
2. **单一基准 `gpts`**：基准词自身衰退会让所有尺寸虚高；没有 ≥1000 月搜的通用词时基准无法校准，名字就没有日搜（真实报告就是这样）。
3. **搜索量滞后约 2 个月**：新词通常没量，`min_volume=50` 会把大部分提议丢掉；表薄是结构性的，不是当天没机会。
4. **名字抽取靠大小写**：全小写、全大写、非拉丁、图片/视频里的名字都会漏；judge 救不回来。
5. **真实解析错误**：`kling 4.0 is`（把句首 Is 拼进名字）、`gpt image 2.5`（Krea 推文里的顺带比较）、`connectors com.botrecipe` / `mcpflow` / `wyre`（sitemap slug 碎片）。
6. **同一实体重复**：`muse spark open` 与 `spark open`、`meta omnilingual asr` 与 `omnilingual asr` 各算一条 lead；缺跨信号别名聚类。
7. **「新词?」列语义混淆**：`new = rose and base < 10` 是「Trends 上新」，不是「刚发布」。真实报告里当天发布的 `muse spark open` 被标成「否」。
8. **竞争判断会误伤**：DR 数据缺失时 `weak=None` 直接判 crowded；新词 KD 经常缺失；只查前 8 行。
9. **`known_terms` 子串匹配**：如果填 `"ai"` 会把所有词都隐藏；需要词边界/模糊匹配。
10. **召回有上限**：X 35 个账号 × 20 条、HF top 50、GitHub 2 页、12 个 sitemap；配置之外的新名字看不见。
11. **新站信号当前是坏的**：DataForSEO whois filter 格式被拒；供应侧那一半缺失。
12. **没有 AI 搜索 / 短视频信号**：只读 Google Ads/Trends/SERP；jason 的实战明确说 ChatGPT 推荐能出单，TikTok/Instagram 是源头。

## 七、jason 文章的 3 个额外信号

1. **用户视角词 > 模型词**：他找的是「这个爆款视频怎么做」，不是「Seedance 2.5」。雷达的 name → generic 表方向对，但入口仍是模型/产品名；需要补 TikTok/Instagram/YouTube 评论、Reddit 求助这类用户视角入口。
2. **AI 搜索流量**：ChatGPT/Perplexity 的推荐能直接带来购买。雷达只量 Google，没量 AI 搜索可见性。
3. **速度**：站点第 2 天峰值、第 5 天结束；雷达 3 天后才复读，对最快的一条线太慢。快线应该 24 小时内复读。

## 八、对本项目的定位

**保留：**
- 发现层（X/HF/GitHub/sitemap）+ 名字判断 + 证据 + name→generic 映射。
- 14 天复盘、降级报告、SQLite 记忆、Skills/MCP、成本透明。

**替换/加强：**
- 度量层：Google Ads 量 → 领先指标组合（X 互动、相关搜索、GitHub/HF 速度、Reddit 求助）。
- 基准：单一 `gpts` → 一篮子基准 + 全局归一化。
- 多语言：分词器、locale 参数、账号包、sitemap 包。
- 名字精度：别名聚类、尾词停用、大小写/非拉丁支持。
- 新词定义：first_seen（首次被看到）而不是 Trends baseline。
- 快线复盘：24 小时 + 7 天，而不是统一 14 天。

**砍掉：**
- 页面生产/上站（不在本项目范围）。
- 变现层只作为辅助信号，不作为门槛。
